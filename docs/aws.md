# Trackside on AWS

Trackside runs as one CloudFormation stack, `trackside-mcp`, from `deploy/trackside.yaml`, in ap-southeast-2 (Sydney). Every resource is named `trackside-*` and tagged `Project=trackside`, so the deploy role can tell Trackside's resources from everything else in the account. This page is the AWS story for the Builder mini-challenge: which services, why each one, what each role may touch, where the data sits, and how the stack looks after itself. Everything here is read from the template, `deploy/deploy.sh` and the crates. Where a figure cannot come from the repository (cost), it is marked as an estimate and says what it assumes. `scripts/check-aws-doc.py` keeps the service table and the template in step.

## Services

Hackathon traffic, for the cost column: about 1,000 requests a day to the API (judges, the simulator's own tool calls, smoke runs and the hourly probe's checks), about 50 simulator turns a day (each one or two Bedrock calls and one Polly call), two snapshot rebuilds and 24 probes. None of these figures is measured; they are the basis of the estimates below, which come from the shape of each service's pricing (per request, per GB-second, per token, per character) rather than from a bill. The project's own expectation is cents a day.

| Service | Created by (resource types in `deploy/trackside.yaml`) | Job in Trackside | Why this, not an alternative | Daily cost at hackathon traffic (estimate) |
| --- | --- | --- | --- | --- |
| AWS Lambda | `AWS::Lambda::Function` x3 (`trackside-mcp`, `trackside-sim`, `trackside-refresh`), `AWS::Lambda::Permission` x4 | Runs the MCP server (1024 MB, 20 s), the simulator (512 MB, 29 s) and the snapshot rebuild plus hourly probe (2048 MB, 900 s), each a Rust binary on `provided.al2023`, arm64 | MCP in stateless JSON mode is one request, one response, so nothing needs to run between requests and there are no instances to patch; the refresh is a 15-minute batch job twice a day, which a container service would bill for all day | Zero: 1,000 one-second calls at 1 GB plus two 15-minute rebuilds at 2 GB is about 140,000 GB-seconds a month, inside the always-free 400,000 GB-seconds and 1 million requests |
| Amazon API Gateway | `AWS::ApiGatewayV2::Api` (`trackside-mcp`), `::Integration` x2, `::Route` x3, `::Stage`, `::DomainName`, `::ApiMapping` | The public HTTPS front door: `/mcp` to the MCP function, `/sim` and `/sim/*` to the simulator, throttled at 10 requests a second (burst 20), on the custom hostname | An HTTP API costs less and routes more simply than a REST API; a bare Lambda function URL has no throttle, no custom hostname with its own TLS policy and no 5xx metric; the trade-off, recorded in the friction log, is the 30 s integration ceiling and buffered responses | Cents a month: HTTP APIs are priced per million requests and 30,000 requests a month is three percent of one million; zero in an account still in its first-year free tier |
| Amazon Cognito | `AWS::Cognito::UserPool` (`trackside-users`), `::UserPoolDomain`, `::UserPoolResourceServer`, `::UserPoolClient` x3 (`trackside-service`, `trackside-user`, `trackside-smoke`) | The OAuth 2.1 authorization server Alexa+ expects: client credentials for discovery (`trackside/mcp:service`), authorization code with PKCE for tool calls as a signed-in user (`trackside/mcp:tools`), a hosted sign-in page, and the signing keys the server checks tokens against | Alexa+ needs pre-registered clients, PKCE with S256 and a 401 that points at metadata; Cognito gives the clients, the hosted page and the keys without writing an authorization server; what it lacks (RFC 8414 metadata) the server publishes itself | User pools are priced per monthly active user with a free allowance that a few judges and testers stay inside; the two client-credentials clients are priced separately per client and per token, so Cognito is the line most likely to show dollars rather than cents on a monthly bill (read the account's bill) |
| Amazon DynamoDB | `AWS::DynamoDB::Table` (`trackside-listeners`: on-demand, encrypted, point-in-time recovery, kept when the stack is deleted) | Listener memory: one item per Cognito subject with the horses they follow, their home state and the day they last heard their stable report; `forget_me` deletes it | One read and one write per request, by one key, with nothing to provision; on-demand billing is zero while nobody asks; a single JSON object in S3 would need read-modify-write across concurrent requests | Fractions of a cent: on-demand reads and writes are priced per million request units, and a few hundred a day is far below that; the items are a few kilobytes |
| Amazon S3 | No template resource: `deploy/deploy.sh` creates the private bucket `trackside-<account>-<region>` (public access blocked, tagged) and the template takes its name as `ArtifactBucket` | Holds the three Lambda zips under `lambda/` and the racing snapshot at `snapshots/latest.json.gz`, which the MCP function reads at cold start and the refresh rewrites twice a day | The snapshot is one gzipped file rebuilt whole, which is what an object store is for; CloudFormation also loads Lambda code from S3 | Well under a cent: a few megabytes stored and a few hundred reads a day, inside the first-year free tier in a new account |
| Amazon Bedrock | SDK call, no resource: `aws-sdk-bedrockruntime` Converse from `crates/trackside-mcp/src/summary.rs` and `crates/trackside-sim/src/agent.rs`, allowed by `bedrock:InvokeModel` in the MCP and simulator roles | `explain_race` has a model reword its facts for the ear (six-second timeout, template fallback); in the simulator a Claude model plays Alexa+: it reads the server's tool list, picks tools and writes the answer | Converse is one request shape for tool use across models; the `au.` inference profile keeps inference in Australian regions; calling the model inside the account keeps credentials and data under IAM rather than behind an outside API key | Cents: about 100 calls a day (50 simulator turns, 50 explanations), each a few thousand input tokens and a short answer, is a few hundred thousand tokens a day at a small model's rate (the Bedrock pricing page has the current per-token price) |
| Amazon Polly | SDK call, no resource: `aws-sdk-polly` `SynthesizeSpeech` in `crates/trackside-sim/src/voice.rs`, allowed by `polly:SynthesizeSpeech` in the simulator role | Speaks the simulator's answers in the Australian English voice Olivia (generative engine, neural fallback), so a demo sounds like a voice assistant rather than a browser | An Australian voice no browser guarantees; voices are not resources, so this is the one `Resource: "*"` grant in the stack | Cents at most: 50 answers of about 300 characters is 15,000 characters a day, priced per character, with a first-year free allowance |
| Amazon EventBridge | `AWS::Events::Rule` x2 (`trackside-refresh`, `trackside-probe`) with Lambda targets and their `AWS::Lambda::Permission` | Runs the snapshot rebuild at 12:00 and 20:00 UTC and the health probe every hour | A rule with a Lambda target needs no runner of its own; the friction log records that rule crons are UTC only and names EventBridge Scheduler as the fix if the hour of drift ever matters | Zero in practice: 26 invocations a day against pricing per million events |
| Amazon CloudWatch | `AWS::CloudWatch::Alarm` x4 | Four health alarms on metrics Lambda and API Gateway already publish (see Operations) | The metrics exist without code; an alarm is the smallest thing that tells a person before a judge notices | Zero: four standard alarms sit inside the always-free allowance of ten alarm metrics |
| Amazon CloudWatch Logs | `AWS::Logs::LogGroup` x3 (`/aws/lambda/trackside-mcp`, `/aws/lambda/trackside-sim`, `/aws/lambda/trackside-refresh`), 14-day retention | Each function's log; the probe's log names the check that failed | Retention is set in the template so logs cannot grow for ever; `aws logs tail` is the last step of the regression checklist | Zero: a few megabytes a day against the always-free 5 GB a month of ingestion |
| Amazon SNS | `AWS::SNS::Topic` (`trackside-alerts`) and `AWS::SNS::Subscription` (email), only when `AlertEmail` is set | Emails the alarm owner when an alarm goes into ALARM and again when it returns to OK | The one-line way to get an alarm to a person; email needs no app or pager | Zero: email deliveries are free up to 1,000 a month |
| AWS IAM | `AWS::IAM::Role` x3 (`trackside-mcp-lambda`, `trackside-sim-lambda`, `trackside-refresh-lambda`) with inline policies; the deploy role lives outside the template | One role per function, each allowed only what the next section lists; AWS STS issues the deploy role's temporary credentials | Separate roles mean the public function cannot write the snapshot and the refresh cannot read listener memory | No charge |
| AWS Certificate Manager | No template resource: `deploy/deploy.sh` requests the certificate with `aws acm request-certificate` (DNS validation) and passes its ARN in as `CertificateArn` | The TLS certificate for the custom hostname, validated by a DNS record and renewed by ACM | Public certificates are free and renew themselves; nothing to store or rotate | No charge for public certificates |
| Amazon Route 53 | `AWS::Route53::RecordSet` (alias A record), only when `HostedZoneId` is set; `deploy/deploy.sh` also writes the ACM validation CNAME with the CLI | The hostname's DNS when its zone is in this account; otherwise the script prints the two CNAMEs for an outside DNS provider | Alias records to API Gateway answer without query charges, and the script can write them, so a Route 53 zone makes the custom domain a one-run job | Only the zone's flat monthly charge, which exists whether or not Trackside uses it; none when DNS is hosted elsewhere |
| AWS CloudFormation | The stack itself, `trackside-mcp`, deployed by `aws cloudformation deploy` with `CAPABILITY_NAMED_IAM`; there is no `Type:` line for it | Creates, updates and deletes everything above in one command, with `Project=trackside` on the stack and on every resource | One template is the inventory, the review surface and the teardown; `--no-fail-on-empty-changeset` makes a redeploy with no changes a no-op | No charge for AWS resource types |

## Who may touch what

The template creates one role per function, each with an inline policy that names its resources. A fourth role, the deploy role, is created by hand outside the template because its policy carries account ids; the project notes hold it.

- **`trackside-mcp-lambda`** (the MCP server). Write to its own log group; `s3:GetObject` on `snapshots/*` in Trackside's bucket; `dynamodb:GetItem`, `PutItem` and `DeleteItem` on `trackside-listeners`; `bedrock:InvokeModel` on inference profiles in this account and on the Anthropic and Amazon Nova foundation-model ARNs. It cannot list a bucket, read the racing archive, write the snapshot or touch any other function.
- **`trackside-sim-lambda`** (the simulator). Write to its own log group; `bedrock:InvokeModel` on the same ARNs; `polly:SynthesizeSpeech` on `*`, because Polly voices are not resources. No S3 and no DynamoDB: the simulator reaches racing data only the way Alexa+ does, over HTTPS to `/mcp` with the signed-in user's token.
- **`trackside-refresh-lambda`** (the snapshot rebuild and probe). Write to its own log group; `s3:GetObject` and `s3:ListBucket` on the two archive buckets, `hr-<env>-gamble-<account>` and `hr-<env>-sectional-<account>`, and nothing that writes to them; `s3:PutObject` and `s3:GetObject` on `snapshots/*` in Trackside's bucket (Get so the probe can read the snapshot's age); `lambda:UpdateFunctionConfiguration` on `trackside-mcp` alone, which it uses to retire warm instances after an upload. The binary also refuses to upload to any bucket not named `trackside-*`. The friction log notes that the same action would let it change the function's environment, memory or timeout; a narrower action does not exist.
- **`trackside-builder`** (the deploy role) is assumed by the IAM user `trackside-ci`, whose only permission is `sts:AssumeRole` on that role; its access key lives in the build environment, never in the repository. The role may read the archive buckets; do anything to `trackside-*` buckets; manage Lambda, API Gateway, Cognito, DynamoDB, EventBridge, CloudWatch, Logs and CloudFormation resources tagged `Project=trackside`, plus the create calls that happen before a tag exists; manage IAM roles and policies named `trackside-*` only; call Bedrock and Polly (the demo video's narration); manage `trackside-*` SNS topics; and, from an add-on policy for the custom domain, request and describe ACM certificates and read Route 53 zones. It cannot create API Gateway's service-linked role, which an administrator does once per account (see the README). `deploy/deploy.sh` and `scripts/token.sh` assume it when `TRACKSIDE_ROLE_ARN` is set.

What no role can do: write to the racing archive, reach any `hr-*` compute or configuration, or read listener memory from anywhere but the MCP function.

## Data residency

- **Region.** `deploy/deploy.sh` defaults `AWS_REGION` to ap-southeast-2 and creates the bucket with that `LocationConstraint`; `scripts/token.sh` and the snapshot tool default to the same region. The stack, the user pool and its hosted sign-in domain, the table, the three functions, the API (a regional endpoint, also behind the custom domain), the log groups, the alarms and the topic are all in that region, and so are the archive buckets the refresh reads.
- **Bedrock.** `crates/trackside-mcp/src/summary.rs` reads `TRACKSIDE_BEDROCK_MODEL`; unset or empty, `explain_race` never calls Bedrock. It builds its client with `aws_config::load_from_env()`, so the SDK takes the function's own region and role credentials; no region or endpoint is set in code. The string it passes as `model_id` is the template's `BedrockModel` parameter, by default `au.anthropic.claude-haiku-4-5-20251001-v1:0`: a cross-region inference profile whose `au.` prefix routes the request to the model within Australian regions, which is why the IAM grant names foundation-model ARNs in any region (the profile may run the model in a region other than the caller's). The call is Converse with at most 300 output tokens, temperature 0.3 and a six-second timeout; an answer with betting talk, a prediction or a dollar sign is dropped for the template sentence. The simulator (`TRACKSIDE_SIM_MODEL`, same default, same client construction) follows the same path.
- **What the model sees.** The facts the tool gathered: race, conditions, field, recent form. Never a price, and never who the listener is. The memory table holds the Cognito subject, horse names, a state and a date; no names or emails. Polly receives the answer text only.
- **What leaves the account.** Nothing: there is no third-party API in the request path. Judges and testers reach the stack over HTTPS at the custom hostname or the execute-api URL.

## Operations

**Twice-daily refresh.** The EventBridge rule `trackside-refresh` runs `cron(0 12,20 * * ? *)`, that is 12:00 and 20:00 UTC: about 10 or 11 pm in Melbourne after the day's results and about 6 or 7 am with the day's final fields (the hour moves with daylight saving because rule crons are UTC only). It invokes `trackside-refresh`, which rebuilds the snapshot from `SnapshotFrom` (default 2026-09-22) to four days past today in Melbourne, uploads it to `snapshots/latest.json.gz`, and then changes the MCP function's description so warm instances retire and the next request loads the new file. The refresh exists only when the stack is deployed with `HR_ENV` set (the `HasRefresh` condition).

**Hourly probe.** The rule `trackside-probe` runs `rate(1 hour)` and invokes the same function with `{"probe": true}`. The probe checks what a judge would touch: a `tools/list` without a token gets 401 with a `WWW-Authenticate` challenge naming the resource metadata; the authorization-server metadata, Cognito's discovery document and Cognito's keys are all served; `/sim` loads; and the snapshot in S3 is under 26 hours old. The first failure fails the invocation, and the log line says which check. `trackside-snapshot --probe` runs the same checks from a laptop.

**Four alarms**, all in the template:

| Alarm | Metric | Condition | Means |
| --- | --- | --- | --- |
| `trackside-refresh-or-probe-failed` | `AWS/Lambda` `Errors` on `trackside-refresh` | sum >= 1 in one hour; missing data is fine | A rebuild failed, or the probe found the endpoint, Cognito or the snapshot age wrong |
| `trackside-probe-silent` | `AWS/Lambda` `Invocations` on `trackside-refresh` | fewer than 1 in each of three consecutive hours; missing data breaches | The probe itself has stopped running, so the alarm above would stay quiet |
| `trackside-mcp-errors` | `AWS/Lambda` `Errors` on `trackside-mcp` | sum >= 5 in five minutes | The MCP server is failing |
| `trackside-api-5xx` | `AWS/ApiGateway` `5xx` on the API | sum >= 5 in five minutes | The public API is returning server errors |

With `ALERT_EMAIL` set at deploy time, the stack creates the SNS topic `trackside-alerts` with an email subscription (AWS sends a confirmation email first), and every alarm notifies it on ALARM and on OK. Without it the alarms exist and are visible in the CloudWatch console, and no topic is created.

**Custom domain and certificate.** Run `deploy/deploy.sh` once with `TRACKSIDE_DOMAIN` set. The script looks for an issued or pending ACM certificate for that name and requests one if there is none (DNS validation, an idempotency token so a rerun never requests twice, tagged `Project=trackside`). It reads the validation CNAME ACM wants; with `TRACKSIDE_HOSTED_ZONE_ID` it writes that record into the Route 53 zone, otherwise it prints it. It then waits up to about five minutes for the certificate to be issued. Issued, it passes `DomainName`, `CertificateArn` and `HostedZoneId` to the stack, which creates the API Gateway domain name (regional, TLS 1.2), maps the `$default` stage to it and, with a zone, an alias A record; without a zone it prints the hostname to CNAME to (the `RegionalHostname` output). Not yet issued, the stack deploys without the domain and the script says to add the record and run again. The server builds its OAuth metadata URLs from the `Host` header, so the custom hostname and the execute-api URL both work, and later deploys keep the domain.

**Logs.** Fourteen days of retention per function. After a deploy, `aws logs tail /aws/lambda/trackside-mcp --since 10m` should show no `ERROR` lines.

## Deploy in one command

```sh
pip install cargo-zigbuild ziglang awscli && rustup target add aarch64-unknown-linux-gnu
HR_ENV=staging SNAPSHOT_FROM=2026-09-22 SNAPSHOT_TO=2026-09-30 deploy/deploy.sh   # prints the /mcp and /sim URLs
```

`deploy/deploy.sh` cross-compiles the three binaries for arm64, uploads each zip under its content hash, creates the bucket if it is missing, and deploys the stack. It reads these variables:

| Variable | Does |
| --- | --- |
| `AWS_REGION` | Region for everything (default `ap-southeast-2`) |
| `STACK` | Stack name (default `trackside-mcp`) |
| `TRACKSIDE_ROLE_ARN` | Deploy role to assume for every AWS call |
| `TRACKSIDE_BUCKET` | Bucket name (default `trackside-<account>-<region>`) |
| `HR_ENV` | The archive's environment; turns on the twice-daily refresh and the hourly probe |
| `SNAPSHOT_FROM`, `SNAPSHOT_TO` | Also rebuild and upload the snapshot for this date range before deploying (needs `HR_ENV`) |
| `TRACKSIDE_DOMAIN`, `TRACKSIDE_HOSTED_ZONE_ID` | Serve the API on this hostname; write its DNS when the zone is in Route 53 here |
| `TRACKSIDE_SIM_TODAY` | The date the simulator treats as today, for demos on a snapshot of past racing |
| `SIM_MODEL` | The simulator's Bedrock model or inference profile (default: the `au.` profile above) |
| `ALERT_EMAIL` | Create the SNS topic and email the alarms there |

After it prints the URLs, run the smoke test and the regression checklist in [docs/testing.md](testing.md).
